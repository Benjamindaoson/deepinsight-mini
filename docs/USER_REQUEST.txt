这不是一个简单的聊天机器人，也不是把现有 DeepInsight Lite 缩小，而是重新设计一套**轻量、可靠、监测优先、面向商业用户的 AI 情报产品**。

整个方案围绕招聘题目的两个交付要求：可交互的 Python AI Agent，以及 3–6 页业务演示 PPT。

# 一、最终架构决策

我的建议是：

**不用 Agno、LangGraph、CrewAI 等 Agent 框架，但充分利用成熟的开源工具。**

采用以下组合：

| 模块 | 技术选型 | 作用 |
|---|---|---|
| AI Agent | Python + Model SDK + Tool Calling | 自主选择研究工具、分析市场 |
| 数据采集 | httpx + feedparser + Trafilatura | 获取新闻、研究报告和网页正文 |
| PDF 研究 | PyMuPDF | 提取研究报告中的文本和页码 |
| 页面变化监测 | Python 内容指纹，必要时接 changedetection.io | 识别数据源更新 |
| 任务调度 | Linux systemd timer / Windows Task Scheduler | 每天早晚自动执行 |
| 数据持久化 | SQLite | 保存来源、指标、历史、事件和报告 |
| 通知引擎 | Apprise + SMTP | Telegram、邮件及其他通知 |
| Web 产品 | FastAPI + Jinja2 + HTMX | 轻量但专业的业务界面 |
| 高质量报告 | Jinja2 + HTML/CSS + Playwright PDF | 自动生成专业 HTML、PDF |
| 可视化 | Matplotlib SVG | 生成可核验的趋势图 |
| 自动化验收 | pytest + Playwright | 真实模型与浏览器操作验证 |

选这些工具是有依据的。feedparser 专注 RSS/Atom，Trafilatura 专注网页正文和元数据提取，Apprise 支持多种通知渠道，Playwright 可以将 HTML 页面渲染为 PDF。它们都能作为 Python 项目里的独立组件使用。[GitHub](https://github.com/kurtmckee/feedparser?utm_source=chatgpt.com)

**关于 changedetection.io：** 它确实很适合监测复杂网站，支持网页变化检测、筛选器和通知，也提供 API。但它需要运行另一项服务，所以我建议先用内置内容指纹实现核心监测，仅在普通 HTTP 采集无法满足需求时再接入它。[GitHub](https://github.com/dgtlmoon/changedetection.io?utm_source=chatgpt.com)

## 二、监测应该怎么实现？

这是整个产品的核心。

我建议同时实现三种监测机制。

| 类型 | 监测方式 | 业务价值 |
|---|---|---|
| 新闻事件监测 | 检查新文章、新规划公告、新租赁事件 | 尽早发现市场风险和机会 |
| 指标变化监测 | 保存历史数据，比较不同统计期 | 判断租金、空置率、供应等变化 |
| 来源更新监测 | 识别机构发布新报告或修改已有资料 | 避免错过重要市场信息 |

核心流程：

**定时触发 → 数据采集 → 新旧比较 → 证据核验 → AI 分析 → 生成报告 → 自动推送。**

默认使用伦敦时间：

- **08:00：Morning Market Brief。** 汇总上一次简报以来的新信息、重要指标和市场事件。
- **18:00：Evening Market Update。** 总结白天新增的重要动态和需要关注的问题。
- **重大事件：** 可在下一次定时检查时标记高优先级，满足条件后触发单独预警。
- **没有重要变化：** 正常生成简短的无重大变化摘要，避免 AI 为了写报告而编造内容。

重要的是，监测程序和网页服务独立运行。**即使没人打开网页，只要部署服务器正常运行，定时任务仍然能够执行。**

## 三、业务报告应该是什么样？

不是普通聊天回答，也不是几千字连续文本。

我希望采用专业商业地产研究报告的形式：

**LONDON OFFICE INTELLIGENCE**

*Morning Market Brief | 19 October 2026*

页面顶部展示报告统计截止时间、数据覆盖状态及关键变化数量。

第一部分是 **Executive Summary**，用 3–5 条信息告诉业务经理今天最值得关注什么。

第二部分是 **Market Signals**，用简洁的指标卡、变化箭头和可比趋势图展示租金、空置率、租赁活动和供应变化。只有证据符合标准的指标才能进入图表。

第三部分是 **What Changed & Why It Matters**，列出新事件、变化证据、可能影响的区域及其商业意义。

第四部分是 **Risks & Opportunities**，严格区分已核实事实、AI 推断和待进一步调查的问题。

最后是 **Sources & Methodology**，包含原始来源链接、统计期间、指标定义及数据限制。

每份报告同时提供网页版、PDF 下载版及适合邮件阅读的 HTML 版本。

# 10. 三层变化检测机制

## 10.1 Layer 1：Source Change Detection

检测来源网页、公告、RSS 和研究报告是否发生变化。

需要记录：

- URL
- Canonical URL
- Content Hash
- Fetched At
- Published At
- Document Version
- Previous Hash

不要直接对完整 HTML 进行哈希。

应先尽可能去除：

- 导航
- 广告
- Cookie 提示
- 页面脚注
- 动态时间戳
- 无关推荐内容

然后对标准化后的主要正文计算 SHA-256。

如果正文变化：

创建候选更新。

但注意：

**网页变化不等于市场变化。**

需要进一步分析正文实际变化。

## 10.2 Layer 2：Event Detection

提取事件：

- New Lease
- Planning Approval
- Development Announcement
- Office Relocation
- Pre-let
- Major Refurbishment
- Company Expansion
- Company Downsizing
- New Market Research Report

同一个事件可能被多家机构报道。

必须进行去重。

建议：

第一层：URL / Document ID。

第二层：正文指纹。

第三层：事件实体与时间、地点、类型匹配。

可以在必要时使用 LLM 判断复杂事件是否重复。

但初期不要引入独立向量数据库。

## 10.3 Layer 3：Metric Change Detection

这是市场数据变化识别。

保存：

```text
Metric
Geography
Definition
Period
Value
Unit
Source
Review Status
```

形成历史快照。

当新的有效观察数据出现时：

1. 检查指标定义是否一致。
2. 检查地域是否一致。
3. 检查单位是否一致。
4. 检查统计期间是否清楚。
5. 检查新旧值是否可比。
6. 计算变化。
7. 判断是否达到预警阈值。
8. 创建 Market Signal。

不能用网页采集时间代替指标统计期间。

如果某篇新报告只是重复发布旧数据，不得识别为新市场变化。

数据被修订时，必须保留旧版本和修订记录。

# 11. 事件与数值的审核门禁

必须防止出现“代码全绿，但市场事实不可信”的问题。

区分：

`DISCOVERED`

发现新来源。

`EXTRACTED`

完成结构化提取。

`SOURCE_VERIFIED`

原文、哈希、引文、时间和来源均通过技术核验。

`PENDING_REVIEW`

仍有定义、地域、口径或事实疑问。

`APPROVED`

经过要求的审核，可用于正式定量结论。

`REJECTED`

不符合要求。

`RETRACTED`

原有事实被撤销或失效。

注意：

Source verified 不自动等于 Approved。

不得擅自将待审数值升级为正式发布数值。

对于已经验证的新机构公告，可以在简报中发布明确标注来源的事件摘要。

但对于未经审核的租金、空置率、投资收益等关键定量判断，应保留审查限制。

如果缺少足够的市场事实，系统可以形成：

- 已确认的新来源摘要
- 已确认的市场事件摘要
- 数据缺口说明
- 待审核指标清单

不能生成虚假的完整市场趋势报告。

# 12. Alert Scoring

每条 Market Signal 可以计算优先级。

建议维度：

- Source Reliability
- Geographic Relevance
- Market Materiality
- Recency
- Novelty
- Evidence Completeness

使用可解释的规则评分。

模型可以建议优先级，但最终必须受证据状态和确定性门禁约束。

建议分级：

### CRITICAL

可能对特定资产、区域或业务产生重大影响，且证据充分。

### HIGH

重要市场变化或重大事件。

### MEDIUM

值得持续关注的普通变化。

### LOW

一般新闻或背景信息。

### INFO

来源更新，但没有得到有效市场变化证据。

优先级不能只根据标题中的“重大”“创纪录”等词汇判断。

# 13. 定时监测

默认使用：

`Europe/London`

必须支持英国夏令时和冬令时。

默认任务：

### Morning Brief

每天 08:00 伦敦时间。

执行：

- 检查新来源
- 提取更新
- 与历史状态比较
- 汇总上次简报以来的新变化
- 生成 Morning Brief
- 按已配置的通知策略发送

### Evening Update

每天 18:00 伦敦时间。

执行：

- 检查当天新发布的信息
- 汇总重要变化
- 更新事件状态
- 生成 Evening Update
- 根据配置发送简报

### On-demand Monitor

用户通过界面点击：

Run Monitor Now

立即执行完整检查。

所有触发方式必须复用同一个 `run_monitor()` 入口。

不要写三套逻辑。

## 13.1 调度方案

本地 Windows 开发：

Windows Task Scheduler。

Linux VPS：

systemd service + timer。

每次启动一个独立的 Python CLI 任务。

例如：

```bash
python -m deepinsight monitor --run morning
python -m deepinsight monitor --run evening
python -m deepinsight monitor --run once
```

需要提供可以直接安装的任务配置和相应说明。

不要假设网页服务运行就等于调度器已经运行。

必须分别验收。

## 13.2 并发与幂等

必须防止：

- 两次监测同时写入。
- 同一新闻重复入库。
- 同一变化重复报警。
- 同一报告重复发送。
- 失败重试时产生重复通知。

使用 SQLite 唯一约束、事务和运行锁。

每次执行记录：

- Run ID
- Trigger
- Started At
- Finished At
- Source Count
- New Documents
- New Events
- Valid Signals
- Report ID
- Notification Status
- Error Summary

如果采集部分来源失败，不得将失败解释为“市场没有变化”。

失败来源应标为 STALE 或 FETCH_FAILED。

# 23. 成本控制

尽量降低调用成本。

原则：

**采集和比较尽量使用确定性程序，只有解释复杂变化时才使用模型。**

建议：

1. 没有来源变化，不调用分析模型。
2. 有来源变化但没有业务相关内容，跳过深度分析。
3. 优先复用已保存的研究内容。
4. 相同问题允许缓存结果，但必须标记数据时间。
5. 结构化提取优先使用规则和已知数据结构。
6. 复杂事件再使用 LLM 提取。
7. 每次请求限制 Token 和执行轮数。
8. 设置每日请求数与 Token 预算。
9. 记录模型调用用量。
10. 超过预算自动停止额外调用并报告原因。

预算限制必须真实执行，不能只在配置中声明。

模型失败时：

- 保留已采集事实。
- 保留已识别事件。
- 保留监测运行记录。
- 显示 AI 分析未完成。

不能因为模型失败而丢失监测数据。

如果采用公网部署，必须启用适当认证、HTTPS 和密钥保护。

# 26. 开发阶段与优先级

按以下阶段执行。

**不要先把所有页面画出来，再发现真正的监测不能运行。**

## G0：环境与真实模型连通性

完成：

- 创建独立项目
- 配置虚拟环境
- 安装最小依赖
- 配置真实模型
- 执行一次真实 API Smoke Test
- 输出 Provider、Model ID、调用状态及耗时

验收标准：

真实模型可以返回有效结果。

若 API 不可用：

记录 BLOCKED。

可以继续完成不依赖模型的开发，但不能宣称真实 AI 验收通过。

## G1：真实数据源采集

完成：

- 至少两个可正常访问的独立真实来源
- HTML/RSS 采集
- 必要的 PDF 解析
- 原始文件保存
- 内容指纹
- 来源与引用定位

验收：

运行真实采集。

重跑后不存在重复数据。

能从系统追溯到原始来源。

如果目标来源无法访问，记录原因并换用合法、可靠的替代来源。

## G2：监测引擎

完成：

- 历史快照
- 内容变化
- 新闻去重
- 指标比较
- 证据检查
- 市场信号
- SQLite 持久化

测试：

A：第一次采集建立基线。

B：第二次相同采集没有重复变化。

C：有新增真实文档时正确识别。

D：隔离测试中数值变化能够正确计算。

E：不可比数据被拒绝。

F：数据撤销或来源失效后，不保留错误有效预警。

注意：

隔离合成测试必须明确标记，不能当成真实市场变化。

## G3：真实 Agent

完成：

- 单 Agent
- Tool Calling
- 6 Skills 接入
- 多轮研究
- 真实来源查询
- 证据核验
- 自然语言回答

验收：

模型必须实际调用至少一个 Skill。

输出必须有来源。

能够正确拒绝证据不足的问题。

## G4：报告引擎

完成：

- 统一报告结构
- 专业 HTML 报告
- PDF
- 图表
- 引用
- 风险与机会

# 五、我额外建议 Codex 特别注意的三件事

### 1. 先找到真实、可持续监测的数据源

这比选择哪种 Agent 框架重要得多。

例如，Savills 已公开发布 2026 年第二季度的 Central London Office Market 报告，内容涵盖 Prime/Grade A rents、vacancy、take-up、供应和部分 ESG 指标。这类报告很适合用作第一批真实来源，但必须保留各项指标的口径，不能把同一报告中的不同地域和统计期混在一起。[Savills](https://www.savills.com/research_articles/255800/393427-0?utm_source=chatgpt.com)

ONS 也提供不需要 API Key 的公开数据接口，适合作为宏观指标来源，但需要验证具体数据集及版本。[ONS Developer Hub](https://developer.ons.gov.uk/?utm_source=chatgpt.com)

**Mini 要优先跑通几个高质量来源，而不是先抓取几百份无法核验的资料。**

### 2. 监测不能依赖 LLM 每天重新搜索全部信息

正确做法是：

**程序负责定时检查和发现变化，模型只负责分析新的、值得关注且证据充分的信息。**

这样成本更低、重复通知更少，也更容易判断系统是否真正发现了新变化。

### 3. 报告比聊天界面更重要

对于非技术背景的业务经理，核心体验应该是：

**早上打开邮箱 → 看到一份漂亮的市场简报 → 一分钟了解变化 → 点击进入完整报告 → 必要时向 AI 追问。**

而不是让用户每天打开 AI 聊天窗口，重新问一遍伦敦写字楼市场发生了什么。

## 六、开发优先级建议

| 优先级 | 功能 | 为什么 |
|---|---|---|
| P0 | 真实模型 API 连通 | 保证是 AI Agent，而不是模拟程序 |
| P0 | 真实来源采集 | 保证有内容可以分析 |
| P0 | **历史比较与主动监测** | 体现产品核心差异化 |
| P0 | **专业 HTML/PDF 报告** | 面向业务团队的核心成果 |
| P0 | 真实 Agent Tool Calling | 满足 AI Agent 测评要求 |
| P1 | 每天早晚自动运行 | 完成持续监测场景 |
| P1 | 邮件通知 | 让用户无需主动登录也能获取情报 |
| P1 | 精美 Web 界面 | 支持交互演示 |
| P1 | 3–6 页业务 PPT | 完成第二项正式交付 |
| P2 | Telegram | 增加推送渠道 |
| P2 | changedetection.io 集成 | 增强复杂网站变化检测 |
| P2 | 多用户、权限和企业部署 | 后续扩展，不影响最小 PoC |

**最后的架构判断：**

DeepInsight Mini 不应该是 DeepInsight Lite 的简陋替代品，而应该是一套更聚焦的产品。

Lite 强在系统完整性；Mini 应该强在**真实监测、自动分析、专业简报和低复杂度交付**。

只要把“真实数据采集 → 发现变化 → AI 解释 → 生成专业报告 → 每天早晚推送”这条链路真正跑通，再配合可交互的 Python Agent 和 5 页业务演示材料，就能形成一个范围清晰、符合原题要求的有竞争力的 PoC。
